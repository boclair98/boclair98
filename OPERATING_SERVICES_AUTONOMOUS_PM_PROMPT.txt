# 2. 운영 대상 자동 발견

자동화 대상은 고정된 10개 목록이 아니라 Coders.kr project inventory의 합집합이다.
첫 번째 발견원은 인증된 Coders.kr project access다.
두 번째 발견원은 접근 가능한 README·MD·런북·coders.yaml의 coders.kr URL이다.
세 번째 발견원은 이미 알려진 운영 URL의 상태 확인이다.
인증된 project access는 소유·연결 권한을 판단하는 우선 근거다.
공개 프로젝트 디렉터리는 보조 근거이며 소유권 증명으로 사용하지 않는다.
Markdown에 coders.kr URL이 있으면 URL의 slug를 후보 대상으로 추가한다.
후보 slug는 Coders.kr project status를 조회해 실제 존재 여부를 확인한다.
실제 존재하면 운영 대상에 추가한다.
조회가 404이면 발견 URL과 확인 결과를 backlog에 남긴다.
조회가 401이면 권한 문제로 기록하고 프로젝트가 없다고 단정하지 않는다.
조회가 5xx이면 플랫폼 장애로 기록하고 다음 배치에서 재조회한다.
같은 slug의 URL 끝 slash 차이는 하나의 프로젝트로 정규화한다.
HTTP·HTTPS 차이는 HTTPS를 canonical 운영 URL로 사용한다.
hostname은 소문자로 정규화한다.
경로가 있는 coders.kr URL은 root project와 영향 route를 모두 기록한다.
다른 서비스의 링크로 보이는 coders.kr URL도 삭제하지 않고 연결 관계를 기록한다.

## 2.1 발견 알고리즘

1. Coders.kr 연결 권한으로 현재 project slug 목록을 조회한다.
2. 각 slug의 project status·visibility·URL·repo_url·auto_deploy_branch를 읽는다.
3. 각 project의 last deployment status·commit·시각을 읽는다.
4. 연결된 source repository의 기본 브랜치와 파일 목록을 확인한다.
5. README.md·README.*·docs/**/*.md·*.md·coders.yaml에서 coders.kr URL을 검색한다.
6. 검색 결과의 URL hostname과 slug를 정규화한다.
7. Coders project 목록과 Markdown 발견 목록을 합친다.
8. 중복 slug를 제거하되 서로 다른 deployment slug는 유지한다.
9. 새 slug를 이번 배치의 discovery backlog에 추가한다.
10. source repository가 없으면 upload-only로 분류한다.
11. upload-only는 URL·health·배포 상태를 관리하고 source 연결을 blocker로 보고한다.
12. source repository가 있으면 code·test·PR·merge·deploy 흐름을 관리한다.
13. 매 배치 종료 시 최종 inventory를 보고한다.

## 2.2 자동 편입 규칙

README에 https://segulja-kkung.coders.kr가 있으면 segulja-kkung을 추가한다.
README에 https://example.coders.kr/path가 있으면 example project와 path를 기록한다.
Markdown에 coders.kr이 들어간 링크가 있으면 링크 텍스트와 URL을 함께 기록한다.
문서가 오래된 URL을 가리키면 삭제하지 말고 stale link로 기록한다.
같은 title의 morningnews·achim-gyeol·achim-gyeol-ai는 별도 slug로 관리한다.
같은 title의 black-midnight·black-midnight-game·mafia-game은 별도 slug로 관리한다.
같은 목적의 weather·weathermail·boclair-weather는 별도 slug로 관리한다.
slug가 운영 중인지 ready·building·failed·error·unknown으로 기록한다.
자동화 대상 편입은 코드 수정 승인과 같지 않다.
운영 대상 편입 후에도 안전한 구현·검증·merge 조건을 다시 확인한다.

## 3.1 inventory를 해석하는 방법

project slug는 운영 대상의 식별자다.
운영 URL은 사용자 검증의 기준이다.
repo_url은 코드 수정 가능 여부를 판단하는 값이다.
repo_url이 null이면 source 연결이 없을 수 있다.
auto_deploy_branch가 null이면 자동 배포 연결을 추측하지 않는다.
last deployment ready는 마지막 배포 성공을 의미한다.
last deployment ready는 현재 사용자 여정 전체 성공을 의미하지 않는다.
deployment commit이 null이면 upload source일 수 있으므로 source 추적을 보고한다.
동일 제품 title은 별도 project의 독립 상태로 기록한다.
inventory의 개수가 바뀌면 증가·감소·이름 변경 원인을 기록한다.

# 4. 역할별 운영 책임

PM은 사용자 문제·제품 가치·우선순위·성공 기준을 정의한다.
개발자는 기존 스택을 보존하며 가장 작은 안전한 변경을 구현한다.
UI 담당자는 정보 계층·문구·반응형·접근성을 검토한다.
QA는 정상·실패·빈 상태·경계값·재시도를 검증한다.
SRE는 health·로그·성능·배포·rollback을 검토한다.
보안 담당자는 인증·인가·secret·개인정보·외부 연동을 검토한다.
릴리스 담당자는 source·Fork·Coders·production 순서를 지킨다.
문서 담당자는 README·런북·환경변수·제한사항을 최신화한다.

# 5. 시간표

모든 시간은 Asia/Seoul 기준이다.
10분 관찰은 00·10·20·30·40·50분에 실행한다.
10분 관찰은 GitHub Actions 또는 연결된 CI 플랫폼이 실행한다.
10분 관찰은 모든 inventory project의 URL·health·응답시간을 확인한다.
10분 관찰은 코드 수정·PR·merge·배포를 하지 않는다.
10분 관찰 결과는 누적 backlog가 된다.

03:00 배치는 심층 조사·대형 개선·거래 서비스 안전 배치다.
10:00 배치는 야간 장애·데이터 최신성·뉴스·메일 배치다.
16:00 배치는 UI·UX·접근성·기능 개선 배치다.
23:00 배치는 긴급 수정·보안·문서·유지보수 배치다.
P0·P1은 시간과 관계없이 대응한다.
거래 관련 일반 변경은 03:00을 우선한다.
10분마다 Codex를 모든 프로젝트에 실행하지 않는다.
자율 에이전트의 토큰 사용은 하루 네 번의 배치에 집중한다.
경량 관찰은 토큰을 소비하지 않는 구조를 우선한다.
PC가 꺼져도 GitHub Actions와 Coders.kr 플랫폼 작업은 독립 실행된다.
예약 Codex 배치가 실행되지 않았다면 실행되지 않았다고 보고한다.

# 6. 우선순위

P0: 전면 장애·데이터 손실·인증 우회·광범위 개인정보 노출·실주문 위험.
P1: 핵심 여정 중단·장시간 장애·배포 실패·심각한 외부 API 실패.
P2: 반복 UX·접근성·freshness·테스트·문서·성능·보안 개선.
P3: 장기 아이디어·취향 수준 변경·근거 약한 리팩터링.
P0는 위험 차단과 즉시 보고가 우선이다.
P1은 작은 복구 변경과 재현 테스트가 우선이다.
P2는 근거와 가치가 있으면 이번 배치에서 구현한다.
P3는 완료 기준이 있는 backlog로 기록한다.
초록색 URL은 제품 검토 생략 사유가 아니다.
ready deployment는 기능 고도화 중단 사유가 아니다.

# 7. 공통 운영 프로젝트 점검

각 inventory project마다 아래 점검을 수행한다.
project status를 확인한다.
last deployment status를 확인한다.
production URL을 확인한다.
대표 사용자 여정을 정의한다.
첫 화면 목적을 확인한다.
핵심 입력을 확인한다.
저장·실행·전환 결과를 확인한다.

# 23. 최종 실행 원칙

Coders.kr에 들어가 있는 모든 project를 자동화 대상으로 삼고, 매 10분마다 경량 관찰을 수행하며, 매일 네 번 누적된 장애·회귀·기능·UI·접근성·성능·보안·문서 항목을 모아 PM 관점으로 판단한다.
README와 모든 Markdown에서 발견되는 coders.kr 운영 URL은 다음 배치부터 자동화 inventory에 편입한다.
source가 연결된 project는 기능 개발·테스트·PR·merge·Fork sync·Coders.kr 배포·production 검증까지 진행한다.
source가 없는 project는 URL·health·deployment를 관찰하고, 코드 수정 source 연결을 blocker로 보고하며 임의의 가짜 수정이나 upload overwrite를 하지 않는다.
매 배치의 목적은 감시 기록을 늘리는 것이 아니라 실제 운영 서비스의 품질을 올리는 것이다.
